# Задача 7.1.2 — Property-based тесты (Hypothesis)

## Описание
Дополнить проект property-based тестами на Hypothesis: вместо ручных примеров описать инварианты системы, а библиотека сама подберёт входные данные и последовательности операций для поиска контрпримеров.

## Что нужно знать
- **Property-based тестирование** — вы формулируете правило (свойство), которое всегда должно выполняться, а Hypothesis генерирует входы и проверяет его; при падении минимизирует пример (shrink).
- **Оракул** — источник «правильного» ответа. В задании роль оракула играет «теневая» модель состояния в тесте (обычный словарь), сверяемая с ответами API.

## Обязательные свойства

### 1. «Создание и чтение совпадают»
Для любого валидного пользователя POST `/users` возвращает новый `id`, а GET `/users/{id}` — те же `username` и `age`.

### 2. «Уникальные и монотонно возрастающие id»
Для серии валидных пользователей `id` не повторяются и не убывают (последний ≥ предыдущего).

### 3. «Удаление»
После DELETE `/users/{id}` ресурс исчезает окончательно: повторный DELETE и любой GET по нему дают 404.

### 4. «Негативные границы»
На границах (пустой/очень длинный username, минимальный/максимальный age) система ведёт себя предсказуемо: валидные данные → 201/200, невалидные → 422.

### 5. «Последовательностное (stateful) свойство»
Поведение на последовательностях операций (`create` → `read` → `delete` → …). Реализовать «теневой» словарь-оракул:
- `create` — создаёт пользователя и записывает в оракул;
- `read` — если id есть в оракуле, GET возвращает те же поля; иначе 404;
- `delete` — если id есть, DELETE даёт 204 и удаляет из оракула; иначе 404.

Hypothesis генерирует случайные последовательности этих шагов; после каждого шага API сверяется с оракулом.

## Требования к реализации
- Тесты асинхронные: `httpx.AsyncClient` + `ASGITransport`, без реального сервера.
- Очистка in-memory хранилища перед/после каждого теста.
- Настроить параметры Hypothesis (количество примеров, дедлайн, воспроизводимость) для детерминированных прогонов.
- Основную массу входов генерирует Hypothesis; точечные примеры допустимы для редких кейсов.

## Критерии приёмки
- Property-based тесты реализованы для всех описанных свойств.
- Stateful-тесты сверяют API с оракулом на случайных сценариях; найденные контрпримеры минимизируются.
- Покрыты валидные и граничные/невалидные случаи.
- Тесты изолированы и воспроизводимы; корректная реализация проходит, а внесённые дефекты обнаруживаются.
